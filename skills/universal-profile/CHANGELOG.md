# Changelog

All notable changes to the Universal Profile Agent Skill. Versions follow Semantic Versioning; breaking changes to verb names, arguments or JSON output bump the major version. The bundled data (ABIs, chain and contract registry) carries its own `data-version` in the `SKILL.md` metadata.

## [0.1.0] — Unreleased

First version of the skill.

### Added
- Backups state their PBKDF2 iteration count: new encrypted backups use 600,000 iterations (LSP-30's recommendation) and write the count as `secrets.iterations`, before `data`; the rest of the file is unchanged (version 2, `encryptionType`, AES-256-GCM, 32-byte salt, 16-byte IV, the double-encoded key list). Reading derives with exactly the stated count: a file without it (the app's, and this skill's earlier ones) is read with exactly 10,000, a stated count must be a whole number from 1 to 5,000,000 or the file is refused before any key derivation, and no other count is ever tried (the reader no longer falls back from 10,000 to 600,000). Universal Profile app and extension versions that do not read `secrets.iterations` cannot open a 600,000 file (they report a wrong password): `data.appCompatible` is false for it and `data.say` tells the human. `backup export --legacy` makes an explicitly labelled app-compatible copy at 10,000 (stated), with a LEGACY warning. The export result, its confirmation, `backup inspect`, `backup verify`, `backup list` and the backups index show the count.
- Backups carry the agent's own name: `backup export --bot-name "<display name>"` (or the host's public `UP_AGENT_NAME`) makes the default file `<display name> - universal-profiles-backup-YYYY-MM-DD.json` in every mode; without a name it stays `universal-profiles-backup-YYYY-MM-DD.json` (nothing is guessed or hard-coded). The name is made file-system safe and key-shaped text is refused; an explicit `--path` is used as given; the file format (LSP-30), encryption and import are unchanged, and prefixed backups are still refused by every other file-reading verb. `references/standards.md` no longer says the skill does not use LSP30.
- Rediscovering the profile in a new chat: `profile identity` is a read-only, offline lookup of the saved public state (default profile, every known profile with its address and recorded controllers per network, and the agent's own key addresses, kept apart; saved permissions are never shown as current). No key store access, no network, nothing written or created. SKILL.md tells the agent to run it at the start of every chat, before `up start`, and not to claim it has no profile while one is saved. Chats that share the same state folder (`UP_HOME`) see the same answer; an isolated environment without persistent storage does not, and the verb says so (restore from a backup or have the human authorise the new agent address).
- Swaps and payments stay on the profile: SKILL.md "Swaps and payments as the profile" (who sends, pays, approves and receives on each path, a step-by-step checklist, and what to do when a swap reverts instead of switching to a wallet app or the agent's key), a swap checklist and an `InsufficientETH()` diagnosis in `references/protocols.md`, and a per-path native-value table in `references/execution-paths.md`. Swap-router reverts decode (`InsufficientETH()`, `TransactionDeadlinePassed()`) with hints, and `ERC725X_InsufficientBalance` says to fund the profile, not the gas address. `contract call --value` accepts `lyx`, `lyxt` and `native` like `exec send`; the `exec` verbs warn when a bare `--value` below 1 gwei is read as wei (`--value 5` is 5 wei; write `5lyx`). `--fund-from-controller` with a value now always needs the human's `--approval`, because it spends the agent's gas money.
- Account backups in the Universal Profile mobile app's own format (LSP-30, backup file version 2), byte-compatible with the app apart from the stated iteration count (see the entry above): `backup export` (all profiles and all keys the agent holds, `--profiles` narrows; modes `encrypted`, `public` without keys, and `unencrypted` with `--explicit-consent` and a human approval), `backup list` (which backups exist, whether they cover the current keys and profiles, and a plain-words question to ask the human once), `backup inspect` (what a file holds, never decrypts; re-derives each profile address from the file's deployment data and flags a possible forgery), `backup verify` (opens the file in memory with its password; addresses only; `--online` checks each profile on its networks) and `backup import` (restores keys and profiles; approval always). The encryption is the app's: PBKDF2-HMAC-SHA256 (the count is stated in the file, see the entry above), AES-256-GCM, the double-encoded key list; the reader also accepts the spec's variants (single-encoded object or entry array, 12-byte IV, differently normalised passwords). The backup password may pass through the chat (the file is useless without it; chat is the only channel in cloud agent VMs): it is chosen by the human (12+ characters) or generated (20 random characters, returned once in `data.password` with a plain-language `data.say`). Keys never appear in any output. Files are written to `<UP_HOME>/backups` (0700, files 0600, never overwritten) with an append-only `backups/index.jsonl`, and every other file-reading verb refuses them; the agent delivers a file as a chat attachment by path and never reads it. Restoring follows the app's anti-impersonation rules (a key from the backup still controls the profile on chain, or the file's deployment data proves a key created it) and the permanent-keys rule (keys are recorded before they are stored, never overwritten; a restored key becomes active only if none was set up). `account deploy` suggests a backup once.
- Backup safety (after an independent review): text in a backup file (names, labels, date, password hint, encryption type) is untrusted; anything that looks like a private key is withheld from every result, error and record, and a date that is not an ISO date-time is shown as unknown. Restore checks that need no network (no controller key held, deployment data that does not create the profile) come before any fallback for an unknown or unreachable network, and a deployment proves a key only if it gives it permissions. Each profile in an export lists only its own controllers (other keys are only in the file's secrets), an imported profile can be exported again at once, the path of a new backup is reserved in the index before the file is written (a failed last index line is a warning, never a lost password), and `backup list` never counts a file over the size limit as current.
- Backup safety (second review): `decodedPermissions` property names from a file are never shown (known LSP6 names only, the rest counted); an imported profile's whole record (account, controllers, calldata, manifest) is scanned for private keys before anything is written, and so are an export's destination, hint and account names before consent; held controllers are judged per network (a key listed on one network makes no other network restorable) and a deployment proves a key only with a defined LSP6 permission bit; `profile link` keeps the verified controller of the linked address so a linked account exports with it (and `--refresh` reads the linked address itself); a failed write cancels its path reservation; a temp-file cleanup failure after the backup is written is a warning, never a lost password; `backup list` freshness covers each profile's networks and controllers.
- No false gas requests for relayer-paid profiles: `funding suggest` checks whether a relayer pays for the profile on that network (relayer known, key has EXECUTE_RELAY_CALL, quota read where possible) and then says no gas is needed; only a provably used-up quota leads to a request. `profile status` shows "not needed: the relayer pays gas here"; out-of-gas hints suggest the relay path first.
- SKILL.md opens with a prominent rule, repeated in the references: the profile holds all assets and performs every action; the agent's key only signs and pays gas and is never used as a wallet. User-facing wording: "my profile" vs "my gas address"; funding messages name the gas address.
- Funding: the suggestion follows each network's gas costs (deployment + about 20 actions at the live gas price, rounded to $1/$2/$5/$10; Ethereum mainnet $2–$10) and says in plain words how long it lasts (on LUKSO $1 typically lasts a year or more); `funding suggest --purpose refill` tells the human how much gas the agent has left (with dollar value) and what to top up; out-of-gas errors and `profile status` point to it. SKILL.md: always give dollar values, watch your own gas and ask for a top-up before tasks fail.
- Keys are permanent: the agent's key is the private key of a blockchain account and is never replaced or deleted; additional keys (e.g. one per network, or a new one after a loss, authorised by a co-owner) are kept alongside. Switching the key the agent signs with (`key activate`, also per chain) keeps the previous key in its store and listed as a previous key (`config.previousControllers`; older configs load their earlier keys into it). `key address` lists every key the agent keeps. A key missing from its store is reported plainly by `start`, `init` and `doctor`, with the way back: its backup, or, if truly lost, a new additional key added by a co-owner or admin wallet on each network. `profile status` also checks previous keys when looking for a local key with access on a chain (only keys present in their store are recommended; missing ones are listed as missing). Keys are never lost from the records either: every config write is a fresh read-modify-write under one lock that never drops a listed key; a damaged `config.json` or `keys/candidates.json` stops with a clear error and is never overwritten (a `.bak` copy is kept before each rewrite); every new key is recorded at creation in the append-only `keys/inventory.jsonl` (public addresses only), so a key whose bookkeeping failed, or that could not be read back right after storing, is kept, listed by `key address` and usable with `key activate`; write commands re-read the config after taking the write lock, so they sign with the key that is current.
- Test mode safety: with `UP_TEST_EPHEMERAL_KEY` set, automatic key-store selection always uses the in-memory store, so tests and simulations never write real OS key-store entries. `start --backend` passes an explicit key store through.
- `funding suggest`: how much native coin to ask for on a network: about $1 worth (create the profile plus some gas) or $10 worth (more actions), never below the live deployment cost; live price from CoinGecko (cached, optional), no dollar claim on testnets or without a price; plain-language text. SKILL.md gives the agent the background on why this setup differs from classic wallet apps (for the agent only, never told to the human).
- SKILL.md "Why it works this way": the agent pays its own gas and sends every transaction; the human only funds the agent's address (or uses the relayer / an existing profile) and is never asked to deploy, sign or pay from their own wallet. `account deploy --dry-run` now reports the gas the agent's key needs (`data.gas`: balance, max cost, missing, suggested funding), and a real run stops before signing when gas is missing (`TX_FAILED`, reason `needs-gas`).
- First owners explained: the profile's first owners (the agent's key, plus an optional co-owner wallet added at creation) are part of its address, so they are the only ones with access on networks the profile is deployed to later. Onboarding offers the co-owner option in one short, plain question (optional; the agent's key stays the main path).
- `--admin <wallet>` for `account precompute` / `account deploy`: the human's wallet becomes a full co-controller in the same deployment transaction that the agent's key sends and pays for (the human signs nothing). Onboarding asks for it before computing addresses; SKILL.md: always attach QR images when the human must send, scan or sign, and never tell the human to sign a deployment.
- Guided start (`up start`): one command that silently checks the machine, creates the agent's key if needed (local, no approval), and returns a plain-language opening message (`data.say`) with the onboarding choice, plus agent-only next steps. SKILL.md now starts with conversation rules: take the lead, one question at a time, never mention commands, scripts or internals.
- Funding in onboarding: the controller address is the same on every network, so the agent shows one QR code plus the amount per network (per-network EIP-681 links optional). README: Development section with the `main`/`source` branch model, publishing and porting rules.
- Recommended networks: LUKSO first, then Ethereum, Base, Arbitrum One, BNB Smart Chain and Polygon (★ in `up chains list`, named in `up onboarding options`). `chains list` shows mainnets only unless `--testnets`/`--all`; testnets are used only on the human's explicit request.
- Onboarding choice (`up onboarding options`): own account with the human's gas per network, Universal Relayer (gas included on several networks, separate website; link to be added), or an existing profile. Journeys J1, J2-relayer and J2 in `references/onboarding.md`.
- Distribution: the repository's default branch `main` is exactly this skill with `SKILL.md` at the root (`openclaw skills install git:universal-everything/ai-universalprofile-skill`, `npx skills add universal-everything/ai-universalprofile-skill`, or `git clone` into a skills directory); sources and tests live on branch `source`.
- Agent Skill package `universal-profile`: `SKILL.md`, reference documents (`references/`), bundled ABIs and registry data (`assets/`), single-file Node.js tools (`scripts/up.mjs`, `scripts/up-mcp.mjs`, `scripts/up-doctor.mjs`), MIT-0 license.
- Controller key generated inside the skill and stored in the strongest available key store: macOS login keychain, `systemd-creds`, desktop keyring, Windows DPAPI (also from WSL2), or a protected key file inside cloud agent VMs; fail-closed status reporting; additional keys (e.g. one per network) that never replace or delete an existing key; encrypted keystore backup run by the human only.
- Journeys J1 (agent deploys its own profile through LSP23 at a precomputed address, with identicons and QR funding requests) and J2 (agent joins any existing profile with a recommended permission set).
- One profile across many chains: `profile status` (per-chain overview with next steps, isolated per chain), a per-chain preflight on every write (deployed there, the agent's key a controller there) with chain-specific fixes in the error hints, optional per-chain controller keys (`key activate <address> --chain <id>`), and `profile link` for a profile that has another address on some chain.
- Execution as the profile through the Key Manager, directly through the profile (LSP20), through LSP25 relay calls via LSP15 relayers (with a `chainId` extension for multichain relayers), and through an opt-in ERC-4337 module (EntryPoint v0.6 + `Extension4337`, including deterministic EntryPoint and extension deployment on request).
- Permissions and controllers: all LSP6 permission bits including `EXECUTE_RELAY_CALL` and the ERC-4337 bit 23, AllowedCalls and AllowedERC725YDataKeys encoding, presets, last-controller protection, two-step ownership.
- Tokens: LSP7, LSP8, ERC-20, ERC-721 and ERC-1155 balances, metadata, transfers and approvals with receiver-hook and `force` handling.
- Generic contract interaction on every registry chain: ABI encode/decode, ABI discovery with trust labels (bundled, Blockscout, Sourcify, Etherscan-compatible explorers, proxies, selector databases).
- Registry of the 73 networks with deployed LSP contracts (mirror of lsp-smart-contracts `deployments/` at `16ab2441`), ranked seed RPCs with health checks, failover and Chainlist discovery, protocol addresses, and an egress host list.
- Delegated-autonomy policy with consent levels (`--yes` within policy, `--approval` with the human's words), dry runs and a local audit log.
- Profile metadata (LSP3): `profile metadata show` (decodes the `LSP3Profile` VerifiableURI, fetches the JSON and verifies its hash, optionally every image), `profile metadata set` (name, description, links, tags, profile/background image, avatar; merge by default, `--remove`, `--replace`; PNG/JPEG/GIF/WebP size read in pure JS, SVG refused, 10 MB limit; uploads to IPFS through a swappable provider — Universal Profile IPFS API with an HS256 upload token, Pinata or a Kubo node — then fetches every upload back through the gateway and re-hashes it before writing, fail closed) and `profile url` (profile.link name link, fallback universaleverything.io). Profile metadata always defaults to LUKSO mainnet; another chain only with an explicit `--chain`. `account deploy` and `profile join` prompt the agent to offer metadata when a profile has none. New config keys `ipfs-provider`, `ipfs-gateway`, `ipfs-upload-key`, `pinata-jwt`, `kubo-url`, `kubo-auth` (credentials redacted in `config get`), error code `IPFS_ERROR`, egress category `profileMetadata`.
- LSP26 follower system, ERC-1271 signing as the profile, QR codes (plain address and EIP-681) and blockies identicons generated locally.
- Stdio MCP server exposing every verb as an `up_*` tool and the documents as resources.
- Knowledge verbs `docs` and `standards list`; function inventories of every LSP package and the reference standards.

### Known limitations
- No host has a recorded end-to-end pass on a fresh installation yet; OpenAI dots, Meta Muse and generic Agent Skills hosts are candidates (`references/platforms.md`).
- The optional home-signer bridge (HTTP MCP with OAuth) and the remote-signer backend are not included.
- The `chainId` relay extension is a proposal; relayers that do not implement it are used in legacy mode.
- Profile pictures are uploaded as a single original-size entry (no resized variants: no image codec is bundled). Uploads work out of the box through the Universal Profile IPFS API with the built-in shared key of the universaleverything.io website; the human can override it with their own key, Pinata or a Kubo node.
