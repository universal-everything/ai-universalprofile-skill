# ERC-4337 for a Universal Profile (opt-in)

ERC-4337 lets a profile execute **UserOperations** through an EntryPoint and a bundler. On a Universal Profile it works through the LSP17 extension `Extension4337`. The skill ships this path but **never enables or uses it unless the human explicitly asks for ERC-4337**. The default gasless path is the LSP25 relayer (`references/relayer.md`); ERC-4337 is an additional option, for example when a human wants to use a 4337 paymaster or bundler they already have.

Never pick `--via userop` on your own, never enable it as part of a deployment, and never present it as "the gasless option" unless a paymaster is configured.

## How it works

- `Extension4337` implements `validateUserOp` for **EntryPoint v0.6** (`0x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789`, the legacy `UserOperation` struct with `initCode` and `paymasterAndData`). EntryPoint v0.7 and later use a different struct and selector and do **not** reach this extension.
- The profile maps the selector `validateUserOp` (`0x3a871cdd`) to the extension: data key `LSP17Extension:0x3a871cdd` = `0xcee78b4094da8601109600003a871cdd00000000000000000000000000000000` → extension address.
- **Validation:** the extension checks that the caller is its EntryPoint, recovers the signer from `personal_sign(userOpHash)`, requires **bit 23** (`_4337_PERMISSION`, `0x…00800000`) on that signer, and asks the Key Manager (read-only `lsp20VerifyCall`) whether the signer may perform the UserOperation's `callData`. It does not pay the prefund and has no time range.
- **Execution:** the EntryPoint then calls the profile with the `callData`. The Key Manager now sees the **EntryPoint as the caller**, so the EntryPoint address must itself be a **controller of the profile** with permissions covering what will be executed.
- Effective authority = (signer's permissions, checked at validation with value forced to 0) ∩ (EntryPoint's permissions, checked at execution).

### Trust model, to explain before enabling

*"Enabling ERC-4337 makes the EntryPoint contract a controller of your profile. Anyone who gets a valid UserOperation for this profile through that EntryPoint is limited by the EntryPoint's permissions and by the signer's permissions. I will give the EntryPoint only the permissions I already have for normal work (calls, value transfers, data), never control over controllers, ownership or extensions."*

- Never grant the EntryPoint `CHANGEOWNER`, `ADDCONTROLLER`, `EDITPERMISSIONS`, `ADDEXTENSIONS`, `CHANGEEXTENSIONS` or delegate-call bits. `SUPER_*` bits only if the human explicitly asks after hearing the consequence.
- Use AllowedCalls entries with a wildcard standard for 4337: a non-wildcard standard makes validation call the target's ERC-165, which public bundlers may reject (ERC-7562 rules) and which fails for EOAs.
- LSP25 relay and ERC-4337 can coexist on one profile; their nonces are independent.

## Enable flow (`up account 4337 enable --chain <id>`, admin, per chain)

Run `up account 4337 status --chain <id>` first; it shows EntryPoint presence, extension, registration, permissions, deposit and bundler. Then, with the human's approval for each step that writes:

`up account 4337 enable` performs the missing steps below in order (its `--ep-scope` option chooses the EntryPoint's permissions: `mirror` the agent's own scope, the default for a new EntryPoint controller; `custom`; or `super` only on explicit request). The single steps also exist as separate verbs.

1. **EntryPoint v0.6 on the chain.** The skill checks that code exists at the canonical address and matches the canonical v0.6 runtime code. If it is missing, `up account 4337 deploy-entrypoint --chain <id>` deploys it **deterministically through Nick's CREATE2 factory** `0x4e59b44847b379578588920cA78FbF26c0B4956C` with the canonical creation code and salt, so it lands at the canonical address. Preconditions: the factory exists on the chain, the controller address holds gas for a large deployment (millions of gas), simulation succeeds. If the factory is missing, the skill reports that gap; do not improvise another deployment method.
2. **Extension.** `up account 4337 deploy-extension --chain <id>` deploys `Extension4337(entryPoint)` through the same factory with a fixed salt (same address on every chain for the same EntryPoint), paid by the controller. The bundled registry has no LUKSO-deployed `Extension4337` anywhere; the skill records what it deploys in the local manifest.
3. **Link and authorise** in one `setDataBatch` on the profile: register the extension for `0x3a871cdd` (needs `ADDEXTENSIONS`), add the EntryPoint as a controller with the `entrypoint-4337` preset (needs `ADDCONTROLLER`).
4. **Signer permission:** give the agent's controller bit 23 (`EDITPERMISSIONS`).
5. **Gas:** `up account 4337 deposit --chain <id>` deposits native coin for the profile at the EntryPoint (`depositTo(profile)`), from the profile or from the controller; or configure a paymaster. Without either, UserOperations fail with `AA21`.
6. **Bundler:** `up bundler set <chain> <url>` for a bundler that supports EntryPoint v0.6 on that chain (`eth_supportedEntryPoints` is checked). Without a bundler the skill can **self-bundle** (the controller calls `handleOps` itself). Self-bundling works anywhere the EntryPoint exists but is **not gasless**: the controller pays.
7. **Verify:** the skill simulates validation of a harmless UserOperation and records `4337: enabled` with EntryPoint, extension and deposit in the manifest.

`up account 4337 disable --chain <id>` reverses steps 3–4 (clears the extension key, removes the EntryPoint controller, removes bit 23); `up account 4337 withdraw` returns the deposit to the profile.

## Sending (`up exec userop` or any write verb with `--via userop`)

- The skill builds the UserOperation: `sender` = profile; `nonce` from `EntryPoint.getNonce(profile, key = controller address)`; `initCode` empty (profiles are deployed with LSP23, never through 4337); `callData` = the profile payload (`execute`, `executeBatch`, `setData…`); gas limits from `eth_estimateUserOperationGas`; fees from the chain; `paymasterAndData` from a configured paymaster or empty; `signature` = `personal_sign(userOpHash)` with `userOpHash = keccak256(abi.encode(hash(userOp), entryPoint, chainId))`.
- Batches: one UserOperation with `executeBatch` inside. Avoid `batchCalls` (it would need `REENTRANCY` on the EntryPoint).
- Before contacting the bundler it pre-checks: profile deployed, extension registered with this EntryPoint, signer has bit 23 and the payload permissions, EntryPoint has the execution permissions, deposit or paymaster sufficient.
- Tracking is by `userOpHash` (a different bundler may include it in a different transaction). Execution failure does **not** revert the bundle: the profile still pays, and the receipt carries `success: false` and the decoded revert reason.

## AA error codes (meaning on a Universal Profile)

| Code | Meaning here | Fix |
| --- | --- | --- |
| `AA10`–`AA14` | sender / initCode problems | profiles are deployed with LSP23; `initCode` must be empty |
| `AA21 didn't pay prefund` | no deposit at the EntryPoint and no paymaster (the extension never pays) | `up account 4337 deposit` or configure a paymaster |
| `AA23 reverted: Only EntryPoint contract can call this` | the extension is bound to a different EntryPoint | redeploy/relink the extension for this EntryPoint |
| `AA23 reverted` with `NotAuthorised` / `NoPermissionsSet` | the signer lacks permissions for the `callData` | grant the payload permissions to the signer |
| `AA24 signature error` | bad signature, **or** signer without bit 23, **or** Key Manager refused | check the signer key and bit 23 (`up permissions show`) |
| `AA25 invalid account nonce` | wrong or used nonce | rebuild the UserOperation |
| `AA3x` | paymaster problems | check the paymaster configuration |
| `AA4x` | gas limits / prefund too low | re-estimate |
| `AA5x` | paymaster post-operation problems | check the paymaster |
| `AA9x` | `handleOps` problems (beneficiary, gas values, out of gas, aggregator) | retry with another bundler or self-bundle |

Bundler JSON-RPC errors are reported as `BUNDLER_ERROR`: `-32602` invalid UserOperation, `-32500` rejected in simulation (message contains the `AAxx` code), `-32501`/`-32504`/`-32505`/`-32508` paymaster, `-32502` ERC-7562 rule violation (often an ERC-165 call in validation), `-32503` time range, `-32507` signature.
